# Beta6 replication-retirement qualification

Author: Richard Skinner

Status: **0.5.0-beta6 prerelease**, published on 2026-11-10 after testing on disposable DEV01/DEV02. Stable remains 0.4.9. This record describes lab qualification; publishing does not update production hosts.

## Environment

DEV01 runs Unraid 7.3.4 and DEV02 7.3.2. Both are nested Intel lab guests on one physical host, with different ZFS pool names. All four exact outer storage datasets were snapshotted while both lab hosts were powered off before destructive testing. Existing guests/configuration were preserved. Private helpers, credentials, backups and local instructions are excluded from source/package exports.

New fixtures include an independent Ubuntu guest named **Squid Proxy Beta6 ZFS** with a dedicated qcow2 dataset and small extra zvol, a separate Ubuntu recovery guest, a powered-off raw-disk partial-transfer fixture, a shared-dataset file-fallback fixture, and a tiny unused-policy fixture. Names include spaces. Private NAT was used for the Ubuntu guests, not production addresses.

## Verification results

- The complete privileged Linux `scripts/verify.sh` suite passed against the final runtime source in an isolated staging checkout/mount namespace, including PHP/Bash/Node syntax, native pre-start fencing, restricted transport/chroot/sparse rsync, process identity, existing migration/recovery/TPM/NVRAM, concurrent preparation/cutover, CPU/default/editor, cached inventory and live-migration regressions.
- New shipping-function tests cover 66 retirement/cleanup/ownership/partial/lost-ack checks, 46 incarnation identity/admission/history checks, eight prepared-upgrade checks, 11 cleanup/uninstall checks and executable retirement-dialog/current-cycle-selection tests. Lost responses, stale worker proof, replacement GUID/reservation, missing native authority, running-activation metadata, FUSE/encoded-zvol references and legacy protocol-5 ownership have isolated regression coverage.
- Both hosts accepted a real native Beta5-to-Beta6 install with settings, host identities, pairing keys/pins and the existing Unraid QEMU hook preserved. Successive unpublished builds used an explicit guarded same-version package reinstall rather than pretending that the installed version was older. Final runtime files are compared against the TXZ/source, not merely the UI version label.
- Ordinary replication from a Beta6 source to a Beta5 destination succeeded. Retirement to that older destination was rejected before cleanup, retaining source holds and both destination objects. Updating the destination enabled the capability-gated action; wire protocol remains 7.
- A live Ubuntu source completed replication, keep-retirement, later delete-retirement and Warm Move preparation/removal without restarting during those operations. Its exact QEMU process lifetime, guest boot ID and a persistent canary hash remained unchanged. The source writable dataset, qcow2 disk and zvol were retained.
- Foreign hold, unrelated snapshot and child-dataset fault injections each blocked whole-batch replica deletion. Both replica objects survived; resolving only the test blocker allowed safe retry. A dependent clone also blocked deletion. Unknown state artifacts are retained rather than treated as disposable by directory/name alone.
- Reverse-direction replication was interrupted by stopping only the verified test source worker and pausing/continuing its exact ZFS receiver. A real resumable receive token survived. Keep-retirement retained the token and held source snapshot. Delete without partial-discard approval was blocked; an explicitly approved retry aborted/removed only that receive and released its source base after acknowledgement.
- A READY Warm Move seed with a foreign destination hold became **CLEANUP_BLOCKED**, still showing its original READY preparation result. Both source base holds remained. After releasing only the test hold, retry removed exact destination dataset/zvol data, then released source bases and archived the source logs/record.
- A raw image in a shared dataset selected the ordinary file-copy path. Preparation and cleanup succeeded, preserving the unrelated source file and source disk. Parent directories are not recursively deleted merely because the prepared file was removed.
- An independently created recovery policy armed while its source was stopped, then end-retirement successfully performed coordinated standby disarming before retaining the replica. Retired inventory cannot arm recovery again. An offline destination left a later delete request visibly blocked with scheduling stopped and data retained.
- An unused disabled policy could be removed without touching its VM/storage, then configured again. This record-only path is distinct from an ended policy's terminal receipt.
- Both lab hosts rebooted with licensing USB identity and cached plugin restoration intact. On DEV01, an exact retirement worker was stopped while waiting for its policy lock, then the host rebooted. The durable intent remained, no cleanup resumed automatically, and the browser offered **Retry retirement**. Its authenticated POST completed keep-retirement; later explicit deletion completed as well. Native probes verified pre-QEMU rejection on both hosts after boot.
- Real-browser checks covered styled keep/delete and pinned-retry dialogs, unchecked explicit partial approval, background refresh while the modal stayed open, cancellation and successful submission. A themed-button caption issue found in the browser was corrected and covered by a regression; the full suite passed again after that small JavaScript-only change.
- The reboot test preceded that final caption-only rebuild. The final rebuilt package was guarded-reinstalled on both hosts, all 93 runtime hashes matched, and the corrected caption was verified with uncached browser assets. No second reboot after that JavaScript-only change is claimed. All newly created test guests were left stopped; the temporary receiver-directory field was restored. Exact test replicas/seeds were removed through the new workflow, while source disks, logs/receipts and outer snapshots remain.

## Replication recreation follow-up

- A policy was configured again for the same VM/destination after completed deletion, then again after keeping a verified replica. Each received a new nonce-bound ID, ZFS objects, snapshot names and independent state directory. Two simultaneous same-pair create requests admitted exactly one cycle; later duplicate creation was rejected without modifying history.
- A running Ubuntu source completed a new full copy and a later incremental generation. Its boot ID and existing canary hash remained unchanged through older-cycle deletion. The older cycle's legitimate cleanup and a replayed completed cleanup did not alter the new cycle's destination GUIDs, manifest, state-file hashes or held source bases. The completed replay was rejected by fresh source proof.
- The reverse direction also completed independent cycles while retaining older copies. In a controlled partial case, retirement intent was saved before stopping the exact sender/receiver lifetime, preventing the scheduler from resuming the pending generation. Keep retained a real receive token and its held source snapshot. A separate new cycle completed a full copy beside it. Deleting the old partial without explicit approval was blocked; an approved retry removed only that partial. The newer cycle's exact destination evidence and source base/holds remained unchanged.
- Current-cycle preflight and the real browser's Configure control continued to select the newer cycle while old partial cleanup was blocked. With all cycles ended, the VM's Replicate control opened a fresh ready setup dialog. Browser checks used uncached development assets, found no native popup or console errors, and did not submit unintended configuration changes.
- A recreated policy completed a coordinated standby arm while its source was stopped, then disarmed through retirement. A further cycle was configurable after that retirement. An earlier Beta6 build lacking incarnation capability rejected creation before any new policy/storage mutation. Fresh destination admission also verifies prior cycles' completed receipts and idle recovery; missing/in-flight/mismatched proof has isolated regression coverage.
- The complete privileged Linux suite passed after the recreation changes. Both hosts received the same rebuilt candidate under the normal upgrade guard, with settings, pairing and native hooks preserved. These follow-up tests did not reboot the hosts again or touch production workloads.

An ended cycle remains terminal, but its VM/destination can start a separate new cycle with `replicationIncarnationVersion: 1` on both peers. This starts a full copy, not reuse of the old points/partial receive. Use **Disable** for a reversible pause of the current chain. Kept data remains inert inventory, not a runnable backup. Retained/unresolved cleanup prevents uninstall so ownership records cannot be silently discarded. Legacy unowned preparations are diagnosed but not adopted. The final recreation package contains 94 runtime source files; the earlier reboot/caption-only qualification above used 93.

This work does not qualify physical power loss in the middle of ZFS destruction, every Windows/TPM recovery combination, or retirement of an actually running recovered guest end-to-end. Those unsafe states have isolated fail-closed coverage; they are not claimed as new physical-host qualification. Lost-ack and partial-object replay tests use controlled state-machine fixtures, not network disruption of production hosts. Existing live migration limitations remain unchanged.

The lab also exposed an existing encoded-zvol source-path limitation when a space became `+` in a device symlink; the extra test zvol was renamed before starting the fixture. Cleanup now conservatively recognizes that reference alias, but this is not general support for migrating encoded source zvol paths. Source-side displayed point counts can remain zero even when destination inventory has a verified point; this pre-existing display limitation is not fixed here.
