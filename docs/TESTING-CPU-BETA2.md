# CPU compatibility Beta2 verification

Author: Richard Skinner

## Status

The **0.5.0-beta2** build was qualified on 2026-11-08 for publication as a GitHub prerelease on the beta feed. The stable feed and Community Apps installer remain 0.4.9. The source and companion user guides describe beta availability separately; production packages are not upgraded by this release.

The candidate adds presentation ordering, paired-host suggestions, a one-revision-per-family default view with advanced expansion, an automatic Q35/i440fx overview and reviewed local bulk CPU configuration. Other VM machine families are outside the planned live feature, not newly blocked from existing cold/warm moves. The application updates eligible persistent CPU XMLs, but does not change the virtual chipset, start/stop guests or implement live migration. Wire protocol 7, cached CPU capability version 2 and underlying persistent report schema 2 are unchanged from the Beta1 candidate. The derived overview adds `overviewVersion: 1` on the web side, using the same cached-only wire operation.

## Automated checks

The full `scripts/verify.sh` run passed in an isolated Linux namespace with PHP 8.5.4, Node.js 22.22.1 and Bash, including the native Unraid plugin-manager fixture. No unavailable/skipped checks were reported. This included the existing storage, migration, concurrency, pairing, inventory, API-method, transport and fencing suites, plus:

- 53 CPU-definition and paired-protocol assertions.
- 60 persistent-cache and invalidation assertions.
- 25 saved-machine-scope assertions: empty/unavailable hosts, natural version sorting, VM names containing spaces/markup/Unicode, normal aliases, unsupported families and non-x86/non-KVM classification, unchanged definitions, oversized/malformed XML and symlink refusal.
- 35 automatic-overview assertions: identical-reference aggregation, unknown/different/invalid masks, missing references, changed or malformed identities, oldest timestamps, cross-reference-version host matches, separation from machine-specific observations, and one capability proof plus exactly two cached peer RPCs. Older live-query peers are rejected before dispatch.
- UI regressions for Intel/AMD family ordering, numeric revisions, historical Pentium/486 order and separate synthetic baselines; unknown/deprecated families; exact intersection across all selected peers; pending/offline/unconfirmed peers; fresh pairing snapshots and removed peers; local-only suggestions; retained manual inspection; selector-free requests, out-of-scope VM text, cancellation, escaping and response isolation.
- Collapsed-family regressions: highest exact shared revision rather than a local maximum or a subset-based match; local/unconfirmed fallback when no shared revision exists; local-only expansion with no additional requests; explicit collapse retaining the inspected family; late responses preserving inspected definitions; same-family revision/definition update advice, with no speculative advice for offline peers or different vendors. Malformed optional peer modes/context do not break rendering.

## Initial display-only lab validation

UNRAID-DEV01 used Unraid 7.3.3 and UNRAID-DEV02 used 7.3.2, both with QEMU 10.2.3 and libvirt 12.2.0. All guest VMs remained shut off throughout.

1. Backed up the installed Beta1 descriptors/packages and settings before installing Beta2 using the native plugin mechanism. Checked every installed payload file against the package, exact installed descriptor bytes, native-fence readiness, and unchanged settings, host identities, pairing keys, libvirt hooks, guest XML hashes and power states.
2. Before upgrading DEV02, DEV01's Beta2 read its Beta1 peer's cached CPU report successfully. After both upgrades, paired reads succeeded in both directions. Existing `q35` and `pc` report-file hashes were unchanged: changing presentation/version did not run CPU detection again.
3. Saved-definition inspection identified 29 DEV01 VMs using `pc-q35-9.2` and eight using `pc-i440fx-10.2`; DEV02 had 31 and 12 respectively. The earlier dropdown exercise was superseded by the automatic overview below; exact metadata remains internal and reading it does not start CPU detection.
4. In an earlier iteration, read the previously uncollected `pc-q35-9.2` context locally on each lab. DEV01 initially withheld a suggestion while its peer's cache was unavailable; after both local collections, each host exposed 30 common validated definitions. No paired request launched remote CPU detection. These diagnostic observations were preserved when the selector was removed.
5. Confirmed `Cascadelake-Server-v5`, then v4/v3, precede Skylake and Broadwell in the dropdown and table. The suggested level was `Cascadelake-Server-v5` for the lab pairing. Tested local-only labeling, manual inspection of Broadwell and rejected custom machine input.
6. Corrected the legacy alphabetical fallback and repeated the full automated suite. Refreshed the unpublished iteration through the normal upgrade admission guard, verified every payload file before registering its matching descriptor, and confirmed all existing cached context files and guest/configuration hashes remained unchanged on both labs. This was not replacement of a published release.
7. Reloaded the final browser build and confirmed Pentium III → Pentium II → Pentium → 486, followed by synthetic KVM/QEMU baselines. Saved visual proof of both the recommended modern level and corrected legacy sequence.
8. Qualified the simplified family view with another full verification run. In the live DEV01 browser, 30 validated revisions collapsed to 19 family entries, with Cascade Lake Server v5 first and suggested. Show all revisions restored 30 entries/rows immediately; inspecting v3 and explicitly collapsing returned to v5 in the same family. The cached observation timestamp stayed unchanged.
9. The two labs had different Unraid point versions but the same validated CPU definitions, so the normal view correctly showed no update advice. Different-revision/mask cases and malformed peer data were tested in isolated UI fixtures without falsifying the labs' stored observations. Update advice is informational, not a diagnosis that software must be the cause or authorization to update a host.
10. Removed the selector and qualified the automatic overview with the full Linux suite. Before updating DEV02, the new DEV01 overview combined the older peer implementation's cached `q35`/`pc` reports successfully, requiring no new remote operation. After updating both, each returned 30 shared definitions; local combined reads measured approximately 15–16 ms. The overview timestamp correctly used the older reference observation.
11. Every existing CPU cache file remained unchanged, including additional valid/invalid diagnostic contexts created during user testing. No cache entry was added, removed or recomputed by the paired overview checks. Existing VM definitions, guest states, settings, pairing keys and native hooks were also unchanged by the installs.
12. The final browser showed no machine selector, 19 preferred family entries, 30 entries when expanded, and Cascade Lake Server v5 suggested for the lab pairing. Local-only mode was clearly labeled. Both lab scope inspections reported zero out-of-scope VMs; unsupported-family rendering and classification were covered in fixtures without modifying guest XML. Saved a screenshot of the selector-free page.

Production plugin versions, VM definitions, update feeds and the Community Apps template were not changed. Existing development checkouts were preserved; builds ran in a separate isolated checkout.

## Bulk configuration qualification

The later configuration iteration adds isolated regressions for preserving non-CPU XML, topology/NUMA, default startup checking, guest hypervisor visibility, unused VMX subfeatures, 64-bit requirements, unsupported/malformed CPU settings, recovery-owned XML and QEMU overrides. Service fixtures exercise fresh model/guest validation, schema failures, changed caches/reviews, saved memory states, busy locks, backups before any define, explicit partial failures, successful/idempotent batches and retention of selected versioned names rather than internal baseline aliases. Both new web routes reject non-POST methods. UI fixtures cover immediate styled review, cancellation, stale selections, escaped names, duplicate submission and uncertain network outcomes.

Live bulk tests initially updated 30 eligible definitions on DEV01 and 39 on DEV02, including Q35/i440fx, names with spaces, UEFI and TPM configurations. The final corrected run updated 27 on DEV01 and 39 on DEV02 after existing migration cleanup reduced DEV01's retained source inventory. Non-CPU XML, native autostart, skipped recovery/replication/prepared-work definitions and guest power states were checked independently. Original XMLs and result journals were retained in private backup batches; test definitions were restored conditionally after verification.

Next-boot testing caught hardware expansion data being unsuitable as a forced `check=full` guest definition: latent VMX subfeatures and normal QEMU defaults caused boot rejection despite successful baseline/compare/schema checks. The correction keeps exact model matching and forbidden fallback, freshly validates both hardware level and guest CPU, explicitly handles hypervisor visibility and unused VMX subfeatures, and uses libvirt's normal startup checking. Each lab's 24 supported 64-bit levels was instantiated in a diskless, networkless, paused transient VM and removed before executing guest code; all passed. Six 32-bit levels were excluded. These test-only probes are not part of the application or its normal detection/apply workflow.

The DEV01 browser showed the new live/cold/warm explanation, performance trade-offs and full-stop/start note. Review appeared before validation completed, cancellation discarded late responses, confirmation updated eligible XMLs and showed per-VM results and the backup directory without native popups. The running disposable Squid Proxy guest retained its active CPU after persistent definition changes. After a full stop/start it presented the selected `Cascadelake-Server-v5`, with libvirt automatically recording `check=full` in its live XML. This guest did not reliably respond to ACPI; its test power-offs used the user's standing disposable-VM approval after verifying the outer DEV01 storage snapshots. No production VM or outer-host configuration was changed.

The published release includes its package/installer checksums. Qualification itself did not alter public feeds; publication advances only the beta feed, not stable or production installations.

## Limits

Suggestions use a maintained family preference and descending model revisions, not measured performance or a guarantee of feature-set containment. Unknown future families stay unranked and are not automatically suggested. A higher revision may change mitigation or instruction policies. Cached CPU matches remain display evidence, not permission for an eventual migration.

AMD ordering is covered by fixtures; no new bare-metal AMD boot test or physical CPU replacement was performed. Cache boot reuse remains covered by isolated tests, with native upgrade/service-restart reuse tested directly. No lab-host reboot or guest migration was required. CPU preparation does not certify a future live migration or a guest OS/application's instruction requirements. See the [CPU guide](CPU-COMPATIBILITY.md) and [initial cache qualification](TESTING-CPU-COMPATIBILITY.md).
